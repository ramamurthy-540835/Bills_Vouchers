# GST Easy v3 decisions

- Deploy isolated `preview-v3` web and `api-preview-v3` backend tags with zero production traffic. Existing preview and preview-v2 revisions remain untouched.
- Build frontend from its Dockerfile, not the repository root (root builds FastAPI).
- Customer uploads are real evidence, independent of read-only samples. V3 starts from uploaded canonical bills; no sample is promoted, exported, or persisted.
- Missing GSTIN permits upload/edit but prevents confirmation. Low-confidence extraction requires explicit human review.
- Glossary DOCX is not supplied in the workspace. Use the prompt's minimum glossary, formula and a clearly marked A/B/C matching illustration; do not claim to reproduce missing sections.
- BigQuery partitions by invoice date and clusters by client_id (STRING cannot be a partition key). Gold holds review states; only confirmed rows affect dashboards.
- Production uploads save bronze evidence and a durable job, then return the job ID immediately. The isolated `bills-v3` Cloud Tasks queue performs extraction with stable invoice IDs and a saved silver extraction result for retries. The browser resumes job polling after a reload. Local tests use synchronous processing; Cloud Run does not use in-memory background tasks. Limits: 20 files / 25 MB per request, 1,000 spreadsheet rows / 200 invoices per file, 50 PDF pages.
- Reuse the v6 eligibility engine. Passenger transport exceptions do not make non-GST fuel creditable or override no-ITC rate conditions. Classification is profile-driven, never client-name-driven.
- Rule 46 reference: https://taxinformation.cbic.gov.in/content-page/explore-rules/1000136/1000001
- Backend uses canonical decimal strings and NUMERIC(18,2); XLSX numeric cells are converted through decimal text at the file boundary. AI must emit decimal strings.
- Every API resolves the selected client from authenticated membership; submitted tenant IDs cannot change it. Source downloads are authenticated, not public GCS URLs.
- Cloud Tasks calls the tagged API URL but uses the root service URL as the OIDC audience, as required by Cloud Run. The worker verifies the token and rechecks the uploader's current membership and `can(user, 'bills:write', client_id)` permission. The runtime service account receives queue enqueue permission and permission to act as itself; existing traffic and queues are preserved.
- A preseeded transaction guard serializes invoice writes, including the first invoice for a client. Duplicate financial-year keys and stale versions return a conflict. The simple global guard trades throughput for correctness for this preview; a larger deployment should use tenant-specific preprovisioned guards.
- Missing dates retain the selected upload period until corrected. Rejected bills can be edited and revalidated; confirmation always reruns validation. Reverse-charge confirmation requires a payment reference supplied by admin/tax_admin.
- Invoice-level review and line-level credit calculations are separate. Mixed invoices retain eligible lines while blocked/non-GST purchases appear separately. Unmatched supplier credit notes conservatively reduce available credit. Estimated cash uses the existing IGST/CGST/SGST set-off engine and keeps ECO liabilities cash-only.
- GSTR-2B imports use a new tenant/period-bound canonical matching table. This release accepts B2B invoice records; it does not implement full portal amendment/CDNR ingestion, opening-credit-ledger management, or filing submission. The UI describes the cash result as indicative.
- Runtime Vertex testing required its supported `response_schema` subset rather than the complete Pydantic JSON Schema. The extraction schema remains derived from the canonical model; dates are normalized and incomplete numbers force review.
- No synthetic customer bills are used for live acceptance. BigQuery invoice/matching SQL probes roll back; Vertex verification uses an in-memory image. The queue smoke test writes one empty operational job, not an invoice or accounting entry.
- The current production revisions are checked immediately before deployment. September's older handoff revisions are historical and must not be restored over the current production service.
